# AI-Enabled Micro-channel BTMS: Cloud Prototype

Cloud Computing mini-project, KJ Somaiya School of Engineering.
**Use case:** KJS-CES-02, AI-Enabled Micro-channel Battery Thermal Management System for Electric Vehicles.
**Experiments integrated:** 2 (Docker + Docker Hub), 3 (Kubernetes), 7 (right-sizing), 8 (FinOps instance comparison).

> **Educational prototype.** All data is **synthetic**, generated by a physics-informed lumped
> thermal model of the 10-cell 21700 micro-channel pack described in the use case. It is not CFD
> output and not measured from a real pack. Cooling recommendations are advisory only.

## What it does

`input -> processing -> output`

| Stage | What happens |
|---|---|
| Input | JSON operating condition: mode, C-rate, SOC, state of health, ambient, coolant inlet and pack temperature, Reynolds number (400-700), Al₂O₃ nanofluid vol % (0-2), time window |
| Processing | Validation -> closed-form physics estimate -> grey-box model (physics estimate + gradient-boosting correction) predicts peak cell temperature with a 90 % conformal interval; gradient-boosting models predict cell-to-cell spread ΔT and the likely hotspot cell -> rule-based safety layer -> optimiser searches ~500 coolant settings (Re × φ × inlet temperature) for minimum cooling power that keeps T_max ≤ 40 °C and ΔT ≤ 5 °C |
| Output | JSON + web dashboard: predictions, risk level, hotspot, recommended setpoint, "engineer approval required" flag, optional digital-twin time series |

## Repository layout

```
app/
  physics.py         lumped thermal + hydraulic model of the pack (data generator, digital twin, closed-form prior)
  generate_data.py   writes data/btms_synthetic.csv (20,000 scenarios, seed 42)
  greybox.py         physics prior + ML residual regressor
  train.py           trains/evaluates models, writes models/btms_model.joblib + models/metrics.json
  model.py           inference, safety layer, optimiser, digital twin
  validation.py      input checks (types, ranges, unknown fields)
  api.py             Flask REST API + dashboard
  templates/index.html
wsgi.py, gunicorn.conf.py   production entry point (WORKERS / THREADS env vars)
Dockerfile, .dockerignore   Experiment 2
k8s/                        Experiment 3: namespace, deployment, service, HPA
bench/                      Experiments 7 and 8: load generator, benchmark runner, right-sizing, analysis, pricing
tests/test_api.py           24 tests: representative, invalid-input and failure scenarios
tests/run_scenarios.py      runs the sample scenarios through the API -> results/test_scenarios.json
data/sample_inputs.json     6 valid test scenarios + 5 invalid ones
results/                    measured outputs, figures, test log
docs/                       architecture and data-flow diagrams, demo-video script
report/                     build_report.py (rebuilds the report .docx from results), student.json, screenshots/
```

## API

| Method | Path | Purpose |
|---|---|---|
| GET | `/` | dashboard |
| GET | `/api/health` | liveness/readiness (503 if the model failed to load) |
| GET | `/api/model-info` | model version, features, interval widths |
| POST | `/api/predict` | one operating condition -> prediction + risk |
| POST | `/api/predict/batch` | `{"records": [...]}`, up to 500 |
| POST | `/api/optimize` | recommended Re, φ, inlet setpoint (optional `target_t_max`, `max_delta_t`, `optimise_phi`) |
| POST | `/api/simulate` | digital-twin transient simulation, per-cell temperatures |
| GET | `/metrics` | Prometheus-style request counters |

Example body (also returned by `GET /api/sample`):

```json
{"mode": "discharge", "c_rate": 2.8, "soc_start": 0.95, "soh": 0.75, "ambient_temp": 40,
 "inlet_temp": 32, "start_temp": 37, "reynolds": 450, "phi_pct": 0.5, "duration_min": 20}
```

## 0. Prerequisites (Windows 10/11)

1. **Python 3.13** (python.org installer, tick "Add to PATH").
2. **Docker Desktop** with the WSL 2 backend, running.
3. **minikube** and **kubectl**: `winget install Kubernetes.minikube Kubernetes.kubectl`
4. A free **Docker Hub** account.

All commands below are for **PowerShell**, run from the project folder.

## 1. Run locally (no containers)

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt
python -m app.generate_data            # data/btms_synthetic.csv
python -m app.train                    # models/ + results/figures/ (about 30 s)
pytest -v                              # 24 tests should pass
python tests/run_scenarios.py          # results/test_scenarios.json
python wsgi.py                         # http://localhost:8000  (gunicorn does not run on Windows; the container uses it)
```

## 2. Experiment 2: Docker and Docker Hub

```powershell
$U = "your-dockerhub-username"
docker build -t "$U/btms-api:1.0" .
docker images "$U/btms-api"
docker run -d --name btms -p 8000:8000 "$U/btms-api:1.0"
docker ps                                                  # STATUS shows (healthy) after ~30 s
Invoke-RestMethod http://localhost:8000/api/health
$S = Get-Content data\sample_inputs.json -Raw | ConvertFrom-Json
$body = $S.valid.T2_highway_hot_day_warning | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/predict -ContentType "application/json" -Body $body | ConvertTo-Json -Depth 6
Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/optimize -ContentType "application/json" -Body $body | ConvertTo-Json -Depth 6
# invalid input -> HTTP 422
$bad = $S.invalid.I1_out_of_range_reynolds | ConvertTo-Json
try { Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/predict -ContentType "application/json" -Body $bad } catch { $_.Exception.Response.StatusCode; $_.ErrorDetails.Message }
docker logs btms
docker login
docker push "$U/btms-api:1.0"
docker rm -f btms
```

The dashboard at http://localhost:8000 does the same through buttons (Predict, Optimise cooling, Run digital twin, Send invalid input).

Screenshots for the report: `docker build` finishing, `docker images`, `docker ps` showing **healthy**,
dashboard in the browser, a `422` response from **Send invalid input**, `docker push`, your Docker Hub repository page.

## 3. Experiment 3: Kubernetes (minikube)

```powershell
minikube start --driver=docker --cpus=4 --memory=4096
minikube addons enable metrics-server
(Get-Content k8s\deployment.yaml) -replace 'DOCKERHUB_USER', $U | Set-Content k8s\deployment.yaml
kubectl apply -f k8s\namespace.yaml
kubectl apply -f k8s\
kubectl get pods,svc,hpa -n btms -o wide
kubectl rollout status deployment/btms-api -n btms
minikube service btms-api -n btms --url          # keep this window open; it prints a URL like http://127.0.0.1:5xxxx
```

In a second PowerShell window, using the printed URL:

```powershell
$URL = "http://127.0.0.1:5xxxx"
Invoke-RestMethod "$URL/api/health"              # run several times: "host" changes between pods (load balancing)

# scaling
kubectl scale deployment btms-api -n btms --replicas=4
kubectl get pods -n btms

# self-healing / recovery
kubectl get pods -n btms
kubectl delete pod <one-pod-name> -n btms
kubectl get pods -n btms -w                      # a replacement pod is created; Ctrl+C to stop

# autoscaling under load (watch in one window, load in another)
kubectl scale deployment btms-api -n btms --replicas=2
kubectl get hpa -n btms -w
python bench\loadgen.py --url $URL --concurrency 8 --seconds 180

# failure scenario: bad image tag, then roll back
kubectl set image deployment/btms-api btms-api="$U/btms-api:does-not-exist" -n btms
kubectl get pods -n btms                         # new pod in ErrImagePull / ImagePullBackOff, old pods keep serving
kubectl rollout undo deployment/btms-api -n btms
```

Screenshots: `kubectl get pods,svc,hpa -o wide`, the dashboard through the minikube URL, `host` changing,
scaled to 4 pods, the deleted pod being replaced, `kubectl get hpa -w` showing replicas rising, the ImagePullBackOff
pod while traffic is still served, and `rollout undo`.

## Reproducibility notes

* Seeds are fixed (data 42, load-generator payloads 2026/7), dependency versions are pinned in `requirements.txt`.
* The Docker build regenerates the dataset and refits the deployed model, so the image never depends on a
  pickle built with a different scikit-learn version.
* Benchmark numbers depend on the host. The numbers in the report were measured on a 2-vCPU Linux host,
  where the load generator shares the CPUs with the container. Re-running on your laptop gives different
  absolute values; the procedure and comparisons are the same.

## Limitations (short)

Synthetic surrogate, not CFD or experiment; hotspot location is only moderately predictable without per-cell
sensors; inputs outside the training envelope are rejected; no authentication or TLS on the API.
See the report for the full discussion.
